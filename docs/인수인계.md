## 0. 먼저 알아야 할 것 — 이 문서는 3판이다

2판은 "리디자인 직후, 아직 아무것도 손으로 안 눌러 본 상태" 기준이었다.
그 뒤 실사용 검증과 읽기 전용 감사를 여섯 바퀴 돌면서 **캔버스 기하와
배선 경로를 통째로 다시 지었고, 데이터 왕복과 내보내기를 처음부터 다시 짰다.**
2판을 기억하고 있다면 아래가 다르다.

| 항목 | 2판 | 지금 |
|---|---|---|
| 배선 경로 | React Flow `getSmoothStepPath` | **직접 계산** (`canvas/route.ts`) |
| 레인 | 한 축(centerY) — 실제로는 거의 무시되고 있었다 | **두 축** laneY·laneX + 노드 상자 회피 + 제3의 노드 회피 |
| 커넥터 격자 | 부품 정의 그대로 | **방향에 따라 전치** — 배선이 나가는 변에 핀이 줄지어 선다 |
| PDF 배선 | pdfDraw 가 제 경로를 따로 계산 | **`canvas/wirePlan.ts` 하나** — 화면과 PDF 가 같은 함수 |
| 배선 길이 | 화면마다 따로 해석 | **`store/wireLength.ts` 하나** |
| 구간 길이 | 유도만 (대부분 `—`) | **사람이 직접 입력**(`doc.segmentLengths`) + 유도값과 충돌 시 검증 |
| 불러오기 | `JSON.parse` → `toKit` | **`persistence.parseDocument` 하나** — 고칠 것만 고치고 알린다 |
| 세트 내보내기 | 파일마다 다운로드(27개 중 1개만 떨어졌다) | **ZIP 하나** (`export/zip.ts`) |
| 내보내기 옵션 | 고를 수는 있는데 결과가 안 바뀜 | 여유율·단위·CSV 열이 **실제로 반영** |
| 실행취소 | doc 만 · 50단계 | **{doc, kit} 쌍** · 200단계 |
| 검증 규칙 | 11개 | **22개** |
| 조작 | ⌘+스크롤 확대 · 빈 곳 드래그 박스 선택 | **좌클릭 드래그 = 이동 · Alt+드래그 = 박스 선택 · 핀치/± 확대** |
| 시험 | 341개 | **826개** |
| 시드 부품 | 31종 | **96종** (하우징 55 · 보드투와이어 34 · 터미널 5 · 스플라이스 2) |

**손으로 확인된 것이 늘었다.** 드래그 결선, PDF 3면 구성·한글, 도번·Rev 반영,

실제로 눌러 보고 재 봤다. **여전히 확인 안 된 것**은 §7 에 따로 모아 뒀다.

## 2. 이 툴이 무엇인가

하네스 제작 시 **하우징 선택 → 핀별 선 색 → 상대 커넥터 연결 → 배선도 작성**이
매번 막막한 문제를 해결하는 사내 웹 툴.

핵심 산출물은 **PDF 배선도 + 접속표(From-To) + 파트리스트**.

- 백엔드 없음 (브라우저에서 전부 처리, JSON 파일로 저장/불러오기)
- React 18 + TypeScript + React Flow(@xyflow/react) + Zustand
- 런타임 의존성은 5개뿐: `@xyflow/react` `jspdf` `react` `react-dom` `zustand`
  (ZIP 도 새 의존성 없이 직접 썼다 — `export/zip.ts`)
- GitHub Pages 정적 배포
- 소스 84개(TS/TSX, 그중 시험 39개) + CSS 12개

## 3. 설계에서 반드시 알아야 할 것

### 3-1. 문서는 2층이다 — 세트 / 하네스

**자판기 1대분 = 하네스 A 1개 + B 2개 + C 1개** 처럼, 발주 단위는
하네스 하나가 아니라 **그것들을 묶은 세트**다.

```ts
KitDocument {            // 최상위 저장 단위 (schemaVersion 2)
  harnesses: HarnessDocument[]   // 하네스 여러 종
  set: HarnessSet                // 품번, 세트당 수량, 주문 세트 수
}
```

핵심 설계 판단: **`HarnessDocument` 는 "하네스 한 종"으로 그대로 뒀다.**
캔버스·접속표·속성·핀맵·검증은 전부 하네스 하나만 다루므로,
세트를 위에 감싸는 방식으로 올리면 기존 코드가 손대지 않고 그대로 돈다.

스토어도 같은 원리다. `doc` = 활성 하네스이고, 편집 액션은 전부 `doc` 만
건드린다. 구독 하나가 `doc` 변경을 `kit` 에 되돌려 쓴다(`harnessStore.ts` 하단).
**새 기능을 만들 때도 되도록 이 규칙을 지켜라.**

> **총수량은 절대 저장하지 않는다.** 언제나 `perSet × orderQty` 로 파생한다
> (`store/kit.ts`). 수동 입력 총수량을 두는 순간 화면 숫자와 발주 숫자가
> 갈라지고, 그때부터 아무도 화면을 믿지 않는다.

`schemaVersion 1` 파일은 열 때 자동 마이그레이션된다(`toKit()`).
저장 키를 `harness-tool:doc:v1` / `harness-tool:kit:v2` 로 분리해 뒀고,
읽지 못한 자동저장은 지우지 않고 `harness-tool:kit:v2:broken` 으로 피신시킨다.

### 3-2. 단일 출처 지도 — **이 표가 이 문서에서 가장 중요하다**

같은 사실을 두 곳에서 계산하면 언젠가 반드시 갈라진다. 이번 여섯 라운드에서
난 사고의 절반이 그 부류였다(§8). 그래서 "무엇을 어디서만 정하는가"를
파일 단위로 못박아 뒀다. **여기 있는 식을 다른 파일에 베끼지 마라.**

| 무엇 | 유일한 자리 | 그렇게 한 이유 |
|---|---|---|
| 캔버스 기하 — 격자·핸들 좌표·경계 상자·이름표 글자 | `canvas/geometry.ts` | 같은 격자 코드가 캔버스·속성 패널·핀맵 창·PDF 네 곳에 복사돼 있었고, `offset` 없는 슬롯 하나에 넷이 함께 죽었다 |
| 직교 경로 계산 | `canvas/route.ts` | React Flow 의 `getSmoothStepPath` 는 핸들 조합에 따라 centerY 를 무시한다(실측: `left→right` 만 반영) |
| **문서 → 배선 경로** | `canvas/wirePlan.ts` (`routeWire` · `planWires`) | 화면·PDF·검증(`wire-crosses-part`) 셋이 이 함수만 부른다. 그림이 둘이면 어느 쪽이 맞는지 아무도 모른다 |
| 레인 배정 · 노드 상자 목록 | `canvas/docToFlow.ts` (`assignLanes` · `nodeBoxes` · `laneOffset`) | 상자 폭에 이름표 글자가 들어가므로 배선마다 다시 세면 O(n²) 이 된다 |
| 도면 레퍼런스 J1/SP1/D1 | `canvas/docToFlow.refLabels` | 검증 패널이 가리키는 J2 와 도면의 J2 가 달라지면 안 된다 |
| **배선 길이 해석** | `store/wireLength.ts` | `w.lengthMm ?? cable.lengthMm`. 모르는 값은 `null` 이다 — 0 이 아니다 |
| 하네스 요약 수치(본수·길이 합·미입력 본수) | `store/kit.statsOf` | 검증은 여기서 나온 판정만 "어디인지 짚어준다". 두 곳에서 세면 화면끼리 숫자가 갈린다 |
| 불러오기 검사·정규화 | `store/persistence.parseDocument` | 파일에서 오든 localStorage 에서 오든 전부 이 하나를 지난다 |
| 구간(다발) 산출 · 구간 키 | `physical/segments.ts` (`buildPhysicalModel` · `segmentKey`) | 입력한 구간 길이가 붙는 키를 다른 데서 만들면 어느 구간에도 안 붙는다 |
| 내보내기 파일명·파일 목록 | `export/exportPlan.planExportFiles` | 미리보기와 실제 파일명이 갈라져 `_RevA` 가 빠진 채 나갔다 |
| 치수 단위 변환·여유율 | `export/units.ts` | 화면마다 다른 자리수로 반올림하면 숫자가 갈린다 |
| 접속표 CSV 열 목록 | `export/exporters.RUN_CSV_COLUMNS` | 대화상자 칩도 이 배열에서 나온다 — "칩에는 있는데 CSV 가 모르는 열"이 구조적으로 불가능해진다 |
| 단자 이름 결정 | `export/exporters.terminalNameAt` | 파트리스트 집계와 접속표 '단자' 열이 같은 함수를 쓴다 |
| **부품 분류 · 시리즈 · 역할** | `library/taxonomy.ts` | 그룹 규칙이 패널 안에 있을 때 축이 섞였다(§3-10). 목록·검색·정렬·시험이 전부 이 표 하나를 읽는다 |

### 3-3. 캔버스 기하 두 규칙 (`canvas/geometry.ts`)

**(1) 격자는 방향에 따라 전치된다.** `drawGrid()` 가 배선이 나가는 변에 칸이
많은 축을 붙인다. 1행 10P 커넥터를 0°/180° 로 두면 예전에는 핸들 10개가
높이 38px 변에 **3.8px 간격**으로 몰렸다(20P 면 1.9px). 지금은 30px 간격이다.

**회전이 아니라 전치인 이유**: 좌상단 등록 마크가 "1번 핀 위치"를 뜻한다.
90°·180° 회전은 1번 핀을 다른 모서리로 보내 그 표식을 거짓말로 만든다.
전치는 (0,0) 을 제자리에 두고 긴 축만 세운다.
**저장 데이터(`pinLayout.offset`)는 건드리지 않는다** — 같은 부품을 방향만 바꿔
놓아도 정의가 흔들리면 안 된다.

**(2) 경계 상자에 이름표·MPN 캡션의 폭까지 넣는다.** 이름표는 흰 배경이고
배선은 노드보다 아래층(zIndex 0)이라, 라우터가 모르는 라벨 뒤로 배선이 들어가면
화면에서 통째로 사라진다. overhang 은 **핸들이 없는 쪽으로만** 몬다
(`labelsAlignRight`) — 핸들 쪽으로 넓히면 핸들이 상자 속으로 들어가 스텁부터
회피 대상이 되고 경로가 망가진다.
장치 블록은 좌·우 변이 둘 다 핸들이라 그 수가 안 통해서 **블록 자체를 넓혔다**.

### 3-4. 라우터 (`canvas/route.ts`)

경로 모양은 언제나 이렇다.

```
S ─(스텁)─ A ┐                     ┌ B ─(스텁)─ T
             └───── 주행 구간 ─────┘
```

양 끝은 반드시 핸들 방향으로 곧게 빠져나온 뒤에 꺾인다. 선분은 전부 수평 아니면 수직.

- **레인 두 축** — `laneY` 는 가로 주행 구간의 y, `laneX` 는 세로 간선의 x.
  밀어내기는 **항상 바깥쪽**이라 부호를 접는다(`|lane|`). 그래서 레인 값 자체가
  접힌 뒤에도 크기가 겹치지 않아야 하고, 그 성질은 값을 만드는 쪽
  (`docToFlow.laneOffset` — 음수 쪽만 반 칸 더 민다)이 지킨다.
- **상자 회피** — `pushAside`(주행 구간을 상자 밖으로) · `pushOut`(스텁 연장)이
  자기 두 끝 상자와 **문서의 모든 노드 상자**를 같은 목록으로 다룬다.
  A* 를 쓰지 않았다. 여기서 풀 문제는 "가로 띠 하나를 어느 높이에 놓을까"라는
  1차원 문제이고, 일반 경로 탐색기는 지금 코드가 지키는 성질(직교·스텁 불변·
  레인 분리·결정론)을 전부 다시 증명하게 만든다.
- **끝난다는 근거는 구조로 확보했다** — `pushAside` 는 방향을 처음 한 번만 고르고
  끝까지 유지한다. 매번 가까운 쪽을 다시 고르면 두 무리 사이를 오간다.
- 그래도 못 비키는 병적 배치는 **그리기는 그린다**(선이 사라지는 것보다 낫다).
  그 사실은 검증 규칙 `wire-crosses-part` 가 **최종 경로를 직접 다시 재서** 알린다 —
  라우터의 자기 신고를 받지 않는다. 알고 싶은 것은 "라우터가 시도했는가"가 아니라
  "화면에서 선이 가려지는가"다.

### 3-5. 스플라이스를 특수 케이스로 만들지 않았다

Y자 분기·한 핀 다중 결선이 이 툴의 가장 까다로운 지점이었다. 해법:

- **모든 연결점을 "커넥터"로 통일**한다 (일반/보드투와이어/스플라이스 전부 같은 구조)
- 스플라이스 = `Connector.bridges` 에 "내부적으로 이어진 핀 그룹"을 담은 커넥터
- Y자 분기 = 여러 와이어가 같은 스플라이스를 공유 → 자연히 한 네트
- 한 핀 다중 결선 = 여러 와이어가 같은 `PinRef` 를 공유 → 자연히 합쳐짐

### 3-6. 넷리스트 엔진 (`src/store/netlist.ts`)

union-find 로 **와이어 + 스플라이스 브리지**를 합쳐 전기적으로 이어진 네트를 계산한다.
접속표의 NET 열, 캔버스 하이라이트, 검증의 게이지 불일치가 전부 여기서 나온다.
**이게 이 툴의 심장이다.** 배선 관련 기능을 추가할 땐 여기부터 확인.

### 3-7. 파생 vs 저장 — 네 번 같은 판단을 했다

| 대상 | 판단 | 이유 |
|---|---|---|
| 총수량 | 파생 | 저장하면 화면과 발주가 갈라진다 |
| 배선 레인(laneY·laneX) | 파생 | 도면을 고치면 레인도 따라와야 한다 |
| 물리 뷰 구간(Segment)의 **존재·본수** | 파생 | 저장하면 도면과 구간표가 갈라진다 |
| 구간의 **길이** | **저장** (`doc.segmentLengths`) | 분기가 있는 하네스는 그 구간이 곧 전 경로인 배선이 없어 **유도할 근거가 아예 없다.** 유도할 수 있는 것은 유도하고, 유도할 수 없는 새 사실만 담는다 |

구간 길이의 키는 **구간 양 끝 정점 id 를 정렬한 것**이다. `S1`·`B1` 같은 코드는
작도 순서로 매겨져 배선 한 본만 늘어도 통째로 밀린다 — 어제 넣은 300mm 가
오늘 옆 구간에 붙는다.
`segmentLengths` 는 optional 필드 하나뿐이라 **schemaVersion 은 2 그대로다.**

### 3-8. 무엇을 사는지는 **소속**이 정한다 (길이 출처가 아니다)

케이블에 속한 심선은 케이블 행에 이미 잡혀 있으므로 **전선으로 따로 사지 않는다.**
예전에는 "길이가 케이블에서 왔을 때만" 심선으로 쳤고, 그래서 심선에 길이를 한 번
치면 그 가닥이 전선 720mm + 케이블 300mm 로 **이중 계상**됐다.
심선을 짧게 자르는 것은 **재단 지시이지 구매 지시가 아니다** — 길이칸은 열어 두고
파트리스트가 소속으로 가른다(`export/exporters.buildPartList`).

### 3-9. 문서 자기완결성

`HarnessDocument.usedParts` 에 사용한 부품 스냅샷이 함께 저장된다.
→ JSON 파일 하나만 넘겨도 상대방 쪽에서 도면이 그대로 재현된다.
`parseDocument` 는 이 배열의 **모르는 필드까지 그대로 보존**한다(id·name 없는 것만 뺀다).
검증 규칙 `housing-missing` 이 이 성질이 깨졌는지 감시한다.

### 3-10. 부품 분류는 축이 하나다 (`library/taxonomy.ts`)

부품이 253종이 되자 예전 그룹 목록이 무너졌다. 문제는 개수가 아니라 **축이
섞인 것**이었다 — 용도(`MDB (자판기)`·`LAN`·`USB`), 제조사(`연호 SMH250`),
형태(`범용 하우징`·`와이어투와이어`)가 한 목록에 나란히 있었다. 그래서
"SMH250 압착단자는 어디 있나" 에 답이 없었다(`연호 SMH250` 같기도, `연호 터미널`
같기도 했다. 실제로는 후자였다).

지금은 두 단계뿐이고 각 단계의 축이 하나다.

| 단계 | 축 | 값 |
|---|---|---|
| 계열 `FamilyKey` | 하네스에서 하는 일 | 압착 커넥터 · 규격 I/O · 범용/중계 · 구 항목 |
| 시리즈 `SeriesDef` | 맞물리는 한 벌 | `제조사 · 시리즈 · 피치` (예: `Molex · Mini-Fit Jr. · 4.20mm`) |

세 가지 결정을 함께 기억해라.

1. **한 시리즈 안에 하우징·보드 헤더·압착단자가 같이 산다.** 하네스는 양 끝이
   있어야 그려지고 단자까지 골라야 발주가 되므로, 역할로 칸을 쪼개면 한 벌을
   세 군데서 주워 모아야 한다. 역할(`roleOf`)은 칸이 아니라 **행 안의 표시**이고,
   가로지르고 싶으면 패널 위의 **필터**를 쓴다(축을 늘리지 않고 교차시키는 방법).
2. **용도는 칸이 아니라 태그다.** MDB 부품의 실물은 Mini-Fit Jr 이다
   (39-01-2060 = 5557-06R, 39-30-1060 = 5569). 용도로 칸을 하나 더 파면 같은
   커넥터가 두 군데 살게 된다. 대신 `tags` 로 붙여 검색에서 잡는다.
3. **`match` 는 id 만 본다.** 이름·MPN 은 사람이 고치는 값이라 분류 근거로 쓰면
   오타 한 번에 부품이 목록에서 사라진다.

`taxonomy.test.ts` 가 빠짐·겹침·빈 칸·정렬을 전부 요구한다. 시드에 새 시리즈를
넣고 여기에 한 줄을 잊으면 화면보다 시험이 먼저 깨진다.

> 제조사 순서(`MAKER_ORDER`)는 **적어 둔 것**이다. `localeCompare('ko')` 로
> 정렬했더니 한글이 라틴 문자 앞으로 갔는데, 그건 로케일 구현이 정한 것이지
> 우리가 정한 것이 아니다. 판이 바뀌면 목록 순서가 말없이 뒤집힌다.

### 3-11. 목록에서 암수와 생김새를 글자로 되짚게 하지 않는다

이름 규칙이 제조사마다 달라서, `XHP-10`(암)·`B10B-XH-A`(보드)·`43020`(수) 을
글자만 보고 가려낼 수 있는 사람은 그 시리즈를 이미 아는 사람뿐이다. 그래서 행마다
`library/PartSymbol.tsx` 가 작은 기호를 그린다 — **몸통 = 역할**(래치 상자·기판 위
상자·압착 날개·Y자), **접점 = 성별**(빈 원 = 암/구멍, 찬 원·네모 = 수/각핀),
**배열 = 핀 격자**. 성별 글자는 기호 바로 옆 **고정 폭 칸**에 둔다(행 오른쪽 끝에
두면 이름 길이에 따라 x 가 매 행 달라져 눈이 지그재그로 움직인다).

- **색을 쓰지 않는다.** 이 도구에서 색은 이미 "전선 색"이라는 뜻이 있다.
- **`—`(성별 없음)와 미지정을 구분한다.** 예전에는 둘 다 "배지 없음"이라 확인이
  끝난 부품인지 아직 안 본 부품인지 화면에서 갈리지 않았다. 지금 미지정은 점선
  `?` 로 나온다(현재 2종 — 구 항목의 품번 없는 Mini-Fit·Molex 2x5).

## 4. 건드리면 안 되는 계약

여기 적힌 것은 "취향"이 아니라 **깨면 곧바로 사고가 나는 것**들이다.
전부 한 번씩 실제로 깨져 봤다.

1. **`src/types/index.ts` 는 동결 계약이다.**
   변경 시 `schemaVersion` 과 마이그레이션을 함께 고려하라.
   `drawingNo` `rev` `letter` `segmentLengths` `gender` 처럼 **optional 필드 추가는
   하위호환**이므로 버전을 올리지 않았다. 스토어 계약의 새 액션
   (`addCableForWire` · `syncUsedPart` · `setSegmentLength`)도 전부 optional 로만 얹었다.

2. **선택 모델 불변식 — `ids` 에 원소가 1개인 상태는 만들지 않는다.**
   `store/selectionStore.ts`.
   - `ids.length === 0` → 선택 없음 또는 단일 선택 (`harnessStore.selection` 이 진실)
   - `ids.length >= 2` → 다중. 마지막으로 집은 것이 `selection` 에도 남는다

   그래야 "다중인가?"가 `ids.length > 1` 한 줄로 판정되고 단일 경로가 갈라지지 않는다.
   `setIds` 에서 **ids 를 먼저 놓고 selection 을 맞춘다** — 순서를 뒤집으면 동기화
   구독이 "바깥에서 바뀐 선택"으로 오해해 ids 를 비운다.

3. **배선의 포인터 이벤트는 히트 선이 직접 받는다.**
   `canvas/OrthogonalEdge.tsx` 의 투명 `path.hz-edge-hit` (strokeWidth 12).
   React Flow 의 `onEdgeClick` · `onEdgeMouseEnter/Leave` 에 맡기지 마라 — 둘 다 샜다.
   그리고 `selectionKeyCode`·`multiSelectionKeyCode`·`zoomActivationKeyCode` 중
   **어느 하나라도** 눌리면 React Flow 가 pane 을 활성 모드로 올려 그 클릭을 가져간다.
   그래서 `multiSelectionKeyCode` 와 `zoomActivationKeyCode` 는 `null` 로 못박혀 있고,
   박스 선택은 `selectionKeyCode="Alt"` 로 옮겼다. 수정키 판정은 히트 선이 한다.
   또 `enter/leave` 가 아니라 **`over/out`** 을 쓴다 — 강조가 켜지며 엣지가 다시
   그려지면 원래 DOM 노드의 leave 가 영영 오지 않는다.

4. **화면 = PDF.** 배선 경로는 `wirePlan.routeWire` 하나에서만 나온다.
   좌표계 변환(px → pt)은 PDF 쪽에서만 한다. 상수(`DEFAULT_STUB` 등)를 pdfDraw 에
   베끼지 마라 — 예전에 `STUB_OUT = 14` 를 따로 적어 뒀다가 두 그림이 갈라졌다.

5. **`addConnector` → `addUsedPart` 순서.**
   `addUsedPart` 는 **히스토리를 쌓지 않는 부수 액션**이다. 짝이 되는 편집을 먼저
   부르면 앞 액션의 스냅샷에 부품이 아직 없어 ⌘Z 한 번이 둘을 함께 되돌린다.
   반대로 부르면 커넥터만 사라지고 `usedParts` 는 영영 남는다.
   (여기서 스냅샷을 쌓아 해결하지 않는 이유는, 그러면 부품 하나 놓는 한 손동작에
   ⌘Z 를 두 번 눌러야 하기 때문이다.)

6. **실행취소는 `{doc, kit}` 쌍으로 쌓는다.** 둘은 같은 순간에 찍혔으므로 따로
   돌리면 세트가 가리키는 하네스와 편집 중인 하네스가 갈라진다.
   상한 200단계. 세트 이름 타이핑은 `pushSetHistory` 가 한 덩어리로 묶는다.

7. **접속표 CSV 의 기본 7열은 발표된 인터페이스다.**
   `wire,net,from,to,color,gauge,length_mm` — 받는 쪽 엑셀 매크로가 참조한다.
   `RUN_CSV_DEFAULT_COLS` 의 순서를 기본 헤더와 글자 하나까지 맞춰 뒀다.
   아무것도 안 건드린 사람의 파일이 조용히 바뀌면 안 된다.

8. **여유율은 파트리스트 CSV 에만 붙는다.** 도면 PDF·접속표 CSV 는 **도면 길이
   그대로**다 — 제작자가 자르는 치수가 아니라 설계 치수다.
   `runListToCsv` 에는 여유율 인자를 아예 두지 않아 구조로 막았다.
   적용했으면 머리말이 아니라 **열**로 밝힌다
   (`drawing_length_*` · `order_margin_pct` · `order_length_*`) — CSV 는 엑셀에서
   정렬·필터되고 다른 표에 붙여 넣어지는데 그때 맨 위 한 줄은 떨어져 나간다.

9. **자재표(발주)는 구간 길이를 보지 않는다.** 발주하는 것은 전선 길이지 구간
   길이가 아니고, 구간은 여러 전선이 함께 지나므로 더하면 같은 전선을 구간 수만큼
   다시 센다.

## 6. 디자인·조작 규칙

`src/tokens.css` 가 단일 출처다. **하드코딩 hex 금지.**

1. **UI 강조색은 스틸 `--accent`(#5980a6) 하나.**
2. **빨강은 UI 에서 쓰지 않는다.** 빨강은 전선 색이다. 캔버스에 빨간 배선이
   그대로 그려지므로 UI 가 빨강을 쓰면 구분이 안 된다.
   예외는 삭제 버튼(`--danger`) 하나뿐이다.
3. **밀도 우선.** 컨트롤 26px(보조 22–24px), 본문 12.5px, 표 12px, 최소 10px.
4. **도면 요소는 radius 0**, 컨트롤만 2px.
5. **한글 라벨 기준으로 폭을 잡는다.** 영문보다 길다.
   글자 폭 어림은 `geometry.estimateTextWidth` 하나뿐이고, 화면·PDF·경계 상자가
   같은 값을 쓴다.
6. **정밀 도면에 트랜지션을 넣지 않는다.** 강조 전환은 즉시.
7. 숫자·식별자는 `--font-num`(Barlow) + `tabular-nums`.

### 조작 (`canvas/HarnessCanvas.tsx` 의 ReactFlow props 가 진실)

| 손짓 | 결과 |
|---|---|
| 좌클릭 드래그 (빈 곳) | 화면 이동 |
| **Alt(Option) + 드래그** | 박스 선택 |
| **Shift · ⌘/Ctrl + 클릭** | 선택 집합에 더하기·빼기 |
| 두 손가락 스크롤 | 화면 이동 (`panOnScroll`) |
| 트랙패드 핀치 · 좌하단 ± 버튼 | 확대·축소 |
| ESC | **한 단계씩** — 다중 → 단일 → 없음 |

**⌘+스크롤 확대는 없앴다** (`zoomOnScroll={false}`, `zoomActivationKeyCode={null}`).
그 키를 살려 두면 React Flow 가 수정키 클릭을 pane 으로 가져가 다중 선택이
통째로 깨진다(§4-3).

- 2열 구성, 핀 속성 가로 스트립 상주 / 1번 핀 위치 4택 × 핀 번호 방향 3택
- 캔버스와 동일한 하우징 심볼로 그린다
- **`syncUsedPart`** — 이미 쓰고 있는 부품을 고치면 도면에 반영된다

**물리 뷰 (제조 도면)**
- 구간 자동 산출(배선 그래프 → 최대 신장 숲 → 분기점 삽입)
- **구간 길이 직접 입력** — 입력값이 유도값을 이기되 표에 `입력값` 이라고 밝힌다.
  비우면 되돌아간다. 유도값과 다르면 검증이 짚는다
- 치수선은 **실치수가 확정된 구간에만** 그린다
- 전장은 **끝단↔끝단 최장 경로**(스플라이스 너머 합산). 확정 못 하면 값을 만들지 않고
  `최장 배선` 이라고 사실대로 적는다
- 다발 굵기 = 본수, 분기점 마커(스플라이스=채움 / 단순 분기=빈), 구간표 + 자재 요약

**검증** — **22개 규칙**, 각 지적에 **왜 문제인지** 한 문장.
error → warn → info 순으로 정렬된다.

```
duplicate-id  endpoint-missing  bridge-missing-pin  housing-missing
pin-overflow  pin-multi-wire  terminal-missing  length-missing
floating  splice-underused  std-color-mismatch  self-loop
duplicate-wire  gauge-mismatch
cable-missing  cable-empty  cable-length-missing  cable-core-mismatch  cable-core-spare
segment-length-conflict  segment-length-orphan
wire-crosses-part
```

**출력**
- PDF: 벡터로 직접 그림. 하네스당 **3면 이상**(배선도·접속표·파트리스트, 표가 길면 더).
  한글은 Latin-1 밖 글자만 Canvas 4배 오버샘플 래스터, ASCII 는 벡터 텍스트
- 파일이 2개 이상이면 **ZIP 하나**로 묶는다(무압축 store · UTF-8 EFS 비트).
  진행 중에는 버튼을 잠그고 `7/27` 처럼 세어 보여 준다
- 파일명 규칙 `[세트품번]_[하네스문자]_[종류]_[Rev]` — 미리보기와 실물이 같다
- 내보내기 옵션이 실제로 반영된다: 범위(하네스/세트) · 용지(A3/A4) · 치수 단위(mm/inch) ·
  전선 여유율(0/5/10/직접) · 접속표 CSV 열 선택
- 부품 라이브러리 JSON/CSV 가져오기 (한글·영문 헤더, 잘못된 행만 건너뛰고 사유를 알린다)

**데이터 왕복**
- `parseDocument` 하나가 파일·자동저장을 전부 검사한다. 미래 버전(v3)은 **거부**한다
  (예전에는 v1 로 오해해 세트에 말아넣고 v2 로 덮어썼다 — 되돌릴 수 없다)
- 색 없는 배선에 기본값을 지어내지 않는다. 뺀 뒤 몇 본을 왜 뺐는지 알린다
- 자동저장 QuotaExceeded 를 알린다. 못 읽은 자동저장은 백업 키로 피신시킨 뒤에야 덮어쓴다

## 8. 남은 한계 — **정직하게**

### 8-1. 아직 손으로 확인 안 된 것

- **인쇄물**. PDF 파일은 받아서 렌더까지 봤지만 **실제로 종이에 뽑아 본 적이 없다.**
  흑백 인쇄에서 선 색이 구분되는지, 핀 번호·색 약호가 읽히는지 모른다.
- **A3 / inch / 여유율 조합의 실물**. 여유율 5% 는 값으로 확인했다
  (접속표 800 / 파트리스트 도면 800 · 여유 5 · 발주 840). A4 축소와 inch 표기가
  실제 종이에서 읽히는지는 안 봤다.
- **물리 뷰 구간 나눔이 실제 제작 형상과 맞는지.** 알고리즘이 Claude Design 샘플
  5구간 중 4구간을 본수·포함 배선까지 재현하는 것은 확인했지만, 분기가 여럿인
  **실제 하네스**에서 맞는지는 사람이 봐야 한다.
- **실제 엑셀 부품표 CSV 가져오기.** 파서는 시험으로 덮여 있지만 현장 파일로
  넣어 본 적이 없다.
- **1280px 미만 화면.** 1440×900 이상 전제다.

### 8-2. 데이터·기능이 아예 없는 것

- **자켓이 안 그려지는 배치가 있다.** 자켓은 심선 2본 이상이 **나란히 지나는 구간에만**
  그린다(그래서 사각형이 끝나는 자리가 곧 브레이크아웃이다). 심선이 `JACKET_MAX_GAP`
  이상 벌어지거나 그 사이를 남의 배선이 지나면 그 구간엔 자켓이 없다 — 샘플 문서의
  2심 케이블이 그렇다(스플라이스에서 즉시 위·아래로 갈린다). 화면이 침묵하지 않도록
  케이블 카드가 "지금 배치에서는 자켓이 그려지지 않습니다" 를 밝힌다.
  근본 해결은 레인 배정이 같은 케이블 심선을 서로 이웃하게 놓는 것인데, 라우팅을
  건드리는 일이라 하지 않았다.
- **화면 자켓과 화면 배선의 좌표 출처가 다르다.** 자켓은 geometry 계산 좌표,
  배선은 React Flow 의 DOM 실측 좌표라 몇 px 어긋날 수 있다(`JACKET_PAD` 7px 가 완충).
  PDF 는 둘 다 계산 좌표라 정확히 일치한다.
- **파트 탭에서 케이블 행을 눌러 고를 수 없다**(행에 id 가 없다). 케이블을 고르는
  통로는 캔버스의 자켓과 검증 탭 두 곳이다.
- **보호재(슬리브·테이프) 데이터 모델이 없다.** 물리 뷰 구간표에 `미지정` 으로 비어 있다.
- **레인 수동 조정이 없다.** 자동 배정만 있고 드래그로 옮겨 고정(`laneOverride`)할 수 없다.
- **하네스 요소 단위 복제·이동이 없다.** 하네스 통째 복제는 세트 개요에 있다.
- **커넥터 암수 짝 관리가 없다.** `gender` 필드는 있고 배지·발주 문구에 나오지만,
  "이 커넥터의 상대는 저것" 이라는 관계는 데이터에 없다.
- **핀맵 에디터의 비정형 배치가 없다** (핀을 그리드 밖 임의 위치로).
- **물리 뷰가 PDF 에 없다.** 구간·전장·구간 길이는 화면에만 있다
  (`export/pdf.ts` 주석에 그렇게 적혀 있다). 나중에 더한다면 화면과 같은 산출
  (`buildPhysicalModel`)을 그대로 써야 한다.

### 8-3. 어림·추정임을 알고 쓰는 것

- **`geometry.estimateTextWidth` 는 실제 글꼴을 재지 않는 어림이다.**
  한글 1.0em / ASCII 0.52em 같은 계수로 센다. 이 값이 **경계 상자의 폭**을 정하므로,
  좁게 잡히면 라벨이 상자 밖으로 나가 다시 배선을 덮는다. 라우터가 상자에서
  12px(`route.DEFAULT_CLEARANCE`) 더 띄우는 것이 그만큼의 완충이다.
  **폰트를 바꾸면 이 계수를 다시 봐야 한다.**
- **`REF_BLOCK_H`(17) · `MPN_CAPTION_H`(14) · `DEV_ROW_H`(19) 는 CSS 실측 근사값이다.**
  `canvas.css` 를 고치면 여기도 함께 고쳐야 한다. 몇 px 오차는 레인 배정 결과를
  바꾸지 않지만(레인 간격이 10px 단위) 상자 높이는 그만큼 어긋난다.
- **라우터가 병적 배치에서는 관통한다.** 회피 되풀이 상한(`MAX_AVOID_PASSES = 4`)에
  걸리거나 부품을 서로 겹쳐 놓으면 비킬 자리가 없다. 그때는 그대로 그리고
  `wire-crosses-part` 가 알린다. **자동으로 옮겨 주지는 않는다.**
- **외경(`odMm`)은 `√본수 × 대표 심선 외경` 추정값이다.** 화면에 "추정"이라고 밝힌다.
- **세로 간선 레인(laneX)은 닭-달걀을 한 번만 푼다.** `laneX = 0` 으로 한 번
  그려 본 뒤 그 꺾임 y 를 쓴다. 완전한 동시 해는 범위 밖이다.

### 8-4. 모르는 것

- **여러 브라우저·OS 에서 확인한 적이 없다.** 전부 macOS Chrome 한 곳에서만 봤다.
- **여러 탭 동시 편집은 합쳐지지 않는다.** 마지막 저장이 저장소를 차지하고,
  밀려난 쪽은 `harness-tool:kit:v2:superseded` 에 한 벌 피신해 토스트의
  [밀려난 저장본 내려받기] 로 되찾는다. 자동 병합은 하지 않는다 —
  백엔드 없이 도면을 합치는 건 더 위험하다. 피신 자리는 키 하나라
  마지막으로 밀려난 한 벌만 남는다.
- **한글 래스터 캐시(상한 800)** 가 실제 세트 9종 내보내기에서 몇 번 비워지는지,
  그게 얼마나 느린지 모른다.

## 9. 성능

읽기 전용 감사에서 잰 값이다(순수 함수 구간, 레포 안에 벤치마크는 없다 —
다시 재려면 직접 짜야 한다).

| 규모 | 결과 |
|---|---|
| 실사용 20~50본 | 전 항목 1ms 안팎 |
| 200본 편집 1회 | ~9ms |
| 400본 편집 1회 | ~28ms |

**병목은 `assignLanes` → `planWires`** 다. 구조적으로 그럴 만하다:
`assignLanes` 가 배선마다 `routeOrthogonal` 을 한 번씩 미리 돌리고(세로 간선의
꺾임 y 를 알아야 해서), `colorRuns` 가 이미 배치된 레인 전부와 겹침을 비교한다
(최악 O(n²)). 200 → 400 에서 3배 남짓 느려지는 것이 그 모양이다.

지금 규모(실사용 20~50본)에서는 문제가 아니다. 손대야 할 때가 오면
`colorRuns` 의 겹침 비교를 구간 정렬로 바꾸는 것이 첫 후보다.

### 9-1. 브라우저 렌더 비용 (실측)

위 표는 순수 함수 구간이라 "React Flow 가 실제로 그리는 비용" 은 빠져 있었다.
배선 150본 · 커넥터 30개 문서를 **실제 Chrome 에 띄워** `PerformanceObserver`
(`longtask`) 로 쟀다.

| 무엇 | 결과 |
|---|---|
| 문서 불러오기 + 최초 렌더 | longtask 84 · 140 · **547** · 154 · 57 ms (한 번뿐) |
| 실제 마우스로 배선 위 호버 4회 | **longtask 0건** |

**호버는 실사용에서 문제가 아니다.** 감사가 구조로 짚은 "hover 마다 `docToEdges`
가 다시 돈다" 는 사실이지만, 150본에서도 50ms 문턱을 넘지 않는다.

**한 번 걸리는 곳은 문서를 처음 그릴 때**다(최대 547ms). 사용자가 파일을 열 때
한 번 멈추는 정도이고, 편집 중에는 다시 나타나지 않는다.

주의 — 스크립트로 호버를 연달아 7회 몰아치면(각 회마다 `requestAnimationFrame`
2프레임 대기) 렌더러가 45초 넘게 응답하지 않는 것을 봤다. 사람이 만들 수 있는
입력이 아니라 계측 스크립트가 만든 병목이므로 결함으로 세지 않았지만,
자동화로 이 화면을 두드릴 때는 알아 둘 것.

## 10. 실제로 났던 사고와 교훈 (반복 방지)

### 10-0. 이번 여섯 라운드의 큰 그림

**절반이 "시험은 통과하는데 화면·산출물만 틀린" 부류였다.**
전부 같은 모양이다 — 같은 사실을 두 곳에서 계산했거나, 라이브러리가 우리 값을
조용히 무시했거나, UI 가 말하는 것이 실제로는 안 됐다.
그래서 §3-2 의 단일 출처 표가 생겼고, 새 시험은 대부분 **대조군을 함께 넣는다**
(레인을 끄면 실제로 포개지는지, 상자를 빼면 실제로 관통하는지).

**이 부류를 잡는 방법은 하나뿐이다 — 화면을 실제로 재는 것.**
실제로 그렇게 잡았다:
- 20본 문서를 띄우고 각 경로를 4px 간격으로 훑으며 `elementsFromPoint` 로
  라벨이 위에 있는지 셌다 → 이름표가 배선을 덮는 것을 발견(3,966점 중 3점)
- 최종 경로 점들을 노드 상자와 직접 교차 판정 → 한 줄 배치에서 관통 3본 발견
- PDF 를 `qlmanage` 로 렌더해 화면과 나란히 놓고 눈으로 비교
- ZIP 을 디스크에 떨궈 `unzip -t` · `ditto` · Python 으로 한글 이름 27개 해제

### 10-1. 라이브러리가 우리 값을 조용히 무시한 것

1. **`getSmoothStepPath` 는 핸들 방향 조합에 따라 `centerY` 를 무시한다.**
   `right→left` · `left→left` · `right→right` 무시, `left→right` 만 반영.
   하필 하네스 표준 배치(왼쪽 o=180 → 오른쪽 o=0)가 `right→left` 라
   **우리가 계산한 레인이 화면에 거의 반영되지 않고 있었다.** 20본 두 열 배치에서
   세로 구간 겹침 123쌍, 라벨 좌표가 완전히 같은 쌍 6개.
   → 경로를 직접 그린다. 라이브러리 안쪽 규칙을 우회하는 것보다 짧고 확실하다.

2. **React Flow 는 수정키 하나만 눌려도 pane 이 클릭을 가져간다.**
   ⌘+클릭의 이벤트 대상이 배선이 아니라 `react-flow__pane` 이었다.
   → 세 키를 모두 떼고 히트 선이 직접 받는다.

3. **강조가 켜지며 엣지가 다시 그려지면 `mouseleave` 가 영영 안 온다.**
   상세 카드가 커서를 따라다녔다. → `over/out` 으로 바꾸고 캔버스 밖으로 나갈 때도 끈다.

### 10-2. 같은 사실을 두 곳에서 계산한 것

4. **PDF 가 제 경로 계산을 들고 있었다.** 게다가 읽던 `data.lane` 은 이미
   `laneY`·`laneX` 로 갈린 뒤라 `?? 0` 이 언제나 0 이었다 —
   **PDF 의 레인 분리가 통째로 없었다.** 20본이면 스무 가닥이 한 줄에 포개진다.
5. **격자 코드가 캔버스·속성 패널·핀맵 창·PDF 네 곳에 복사돼 있었다.**
   `offset` 없는 슬롯 하나에 넷이 함께 죽었다. 그 과정에서 pdfDraw 의 180/270 핀
   반전 규칙이 화면과 다른 것도 드러났다.
6. **세트 개요 썸네일이 `boxW/boxH/gridOf` 를 통째로 복제하고 있었다.**
   캔버스 격자를 고친 뒤에도 썸네일만 옛 모양을 그렸다 — 같은 하네스인데 카드와
   도면이 다르게 생겼다. 게다가 축마다 상한이 달라(MAX_COLS 8 / MAX_ROWS 3)
   1열 10행이 1×3 으로 눌려 **가로·세로 비율의 방향이 뒤집혔다.**
7. **길이 해석이 화면마다 달랐다.** 검증은 케이블을 봤고 물리 뷰·`statsOf`·자재표는
   `w.lengthMm` 만 봤다. 한 화면에 "케이블 500mm" 와 "전선 0mm · 길이 미입력 2본" 이
   같이 떴다. → `wireLength.ts` 하나로 모았다.
8. **파일명을 대화상자와 App 이 따로 만들었다.** 미리보기엔 `_RevA` 가 있고 실제
   파일엔 없었다. RevA 와 RevB 가 같은 이름이 되어 받는 쪽에서 덮어써진다.

### 10-3. UI 가 말하는 것과 실제로 되는 것이 어긋난 것 — **최악의 버그**

9. **케이블 길이를 넣을 칸이 아예 없었다.** "길이는 케이블을 따릅니다"라는
   기능의 존재 이유가 UI 만으로는 성립하지 않았다 — 심선을 넣는 순간
   '길이 미입력' error 가 되고 발주가 막히는데, 고칠 길은 JSON 을 손으로 고치는
   것뿐이었다.
10. **케이블을 지울 방법이 없었다.** 심선을 다 빼도 케이블이 남아 자재표가 계속 발주했다.
11. **하네스 BOM CSV 는 체크는 되는데 만들어지는 코드가 아예 없었다.**
12. **세트 27개 파일 중 1개만 받아졌다.** 브라우저가 연속 다운로드를 막는 것을
    툴이 모르고 조용히 넘어갔다. 오류도 토스트도 없다 — 발주처에 1/27 만 보내고도
    모를 수 있다.
13. **내보내기 옵션이 타입 수준에서 잘려 나갔다.** `buildExportEntries` 의 시그니처가
    `{ files, paper }` 라 여유율·단위·CSV 열이 거기서 끊겼다. 대화상자는 제대로
    실어 보냈고 App 도 넘겼는데.
14. 2판 때도 두 번 냈다 — 빈 상태가 "캔버스에 끌어다 놓으라"면서 드롭을 못 받았고,
    "도번을 정해 두면 제목블록에 반영된다"면서 도번 입력란이 없었다.

14-1. **`물리 뷰` 를 눌러도 아무 일이 없었다.** 세 갈래였고 셋 다 시험 전부
   통과 상태에서 났다.
   - 화면 분기가 `hTab === 'set' ? 세트개요 : view === 'physical' ? 물리 : 논리`
     라서, **세트 개요 탭에서는 `view` 를 바꿔도 그리는 것이 안 달라졌다.**
     버튼만 눌린 색이 됐다. → 뷰 토글은 하네스 도면을 가리키는 조작이므로
     세트 개요에서 누르면 활성 하네스로 데려간다(`goView`).
   - **배선 0본이면 `disabled` 였다.** 그런데 물리 뷰는 0본에서도 정상으로 열리고
     "배선이 없습니다 — 핀과 핀을 이으면 구간이 생깁니다" 라고 스스로 안내한다.
     막을 것이 없는데 막고 있었다(그 가드는 PDF 에만 필요하다). → 가드 제거.
   - **상단바에 `:disabled` 스타일이 아예 없었다.** 못 누르는 버튼이 멀쩡한
     버튼과 똑같이 보였고 hover 하면 배경까지 밝아졌다. 이게 "반응 없음" 의
     직접 원인이다. → `button:disabled` 전역 규칙(App.css 맨 끝).

> 세 번째는 CSS 특이도 함정도 함께였다. `button:disabled` 는 (0,1,1) 이라
> `.topbar button { cursor: pointer }` 와 **동점**이다. 파일 위에 뒀더니
> `opacity` 만 먹고 `cursor` 는 안 먹었다(브라우저에서 실측). 그래서 규칙을
> 맨 끝으로 옮겼다 — 특이도를 억지로 올리거나 `!important` 를 쓰지 않는다.

**"눌러도 반응 없음" 은 대개 셋 중 하나다.** ① 상태는 바뀌는데 그 상태를 읽는
화면이 아니다 ② `disabled` 인데 그 사실이 안 보인다 ③ 눌린 게 다른 요소다.
버튼을 막을 때는 **왜 막는지 화면에 남겨라** — 흐리게 + `title`. 그리고
막기 전에 정말 못 쓰는 화면인지 확인하라. 위 두 번째는 멀쩡한 화면을 막은 것이었다.

**안내 문구를 쓸 때마다 그게 실제로 되는지 확인하라.**

### 10-4. 없는 숫자를 지어낸 것

15. **구간 길이가 "그 구간을 지나는 배선 전장의 최댓값"이었는데 티크 달린 정식
    치수선으로 그려졌다.** J1-SP1 100mm 2본 · SP1-J2 150mm 2본에 J1-J2 직결
    900mm 를 얹으면 두 구간 모두 900 으로 찍혔다. 경유 배선의 전장은 구간 길이의
    **상한일 뿐** 근거가 되지 않는다.
16. **전장이 최장 배선 한 본이었다.** 스플라이스로 이어진 500+500 하네스가
    "전장 500mm" 로 나왔다.
17. **자재표가 미입력분을 조용히 0 으로 더했다.** "총 300mm · 3본" 인데 300 은 2본치였다.
18. **세트 카드가 "전선 3본 · 0mm" 로 나왔다.** `statsOf` 는 몇 본치인지까지 들고
    있는데 카드가 합계만 찍었다.
19. **고아 `cableId` 를 아무도 정리하지 않고 아무도 말하지 않았다.** 300mm 로
    재단되던 심선이 조용히 '길이 미상'이 됐다.

→ 규칙: **모르는 값은 `null` 이다. 0 이 아니다.** 합계를 낼 때는 **몇 본치인지**
함께 밝힌다. 추정치는 추정임을 화면에 쓴다. 도면은 발주로 이어지는 문서다.

### 10-5. 잘못된 동작을 시험이 고정하고 있던 것

20. **1행 커넥터의 핸들 4개가 한 점에 겹쳤는데, 그걸 내가 시험으로 못박아 뒀다.**
    원래 `tops.size).toBe(4)` 였던 단언을 재구현 후 통과시키려고 1 로 바꿨었다.
21. **`pdfRoute` 시험에 장치를 빼는 제외 조건이 있었다** — 장치가 못 고쳐진 상태를
    감추던 필터였다.
22. **밀도 픽스처의 스트립 하우징이 1열 N행으로 적혀 있어** 핸들 뭉침 결함을
    비켜 가고 있었다.
23. **"배선이 없으면 물리 뷰·PDF 가 비활성이다" 라는 시험이 있었다.** 물리 뷰까지
    막는 건 결함인데, 시험이 그걸 **정답으로 못박고** 있었다. 그래서 오래 남았다.
    지금은 "PDF 는 막되 물리 뷰는 막지 않는다" 를 요구한다.

→ **시험이 통과하는데 화면이 이상하면 시험을 의심하라.** 고칠 때는 근거를 주석에
남기고, 가능하면 **대조군**(그 수정을 되돌리면 정확히 N건이 실패한다)을 함께 넣어라.
실제로 매 라운드 그렇게 확인했다("HEAD 워크트리에 새 시험만 얹으니 27건이 정확히 실패한다").

### 10-6. 환경

23. **이 Mac 셸에는 `NODE_ENV=production` 이 상시 설정돼 있다.**
    `npm ci` 가 devDependencies 를 통째로 건너뛰어 `tsc: command not found` 가 난다.
    → **`npm ci --include=dev`** 를 써라.
    같은 이유로 vite 가 React 프로덕션 빌드를 물어와 testing-library 의 `act()` 가
    전부 실패했다. `vitest.config.ts` 가 `NODE_ENV='test'` 로 고정해 막고 있다.
24. **CI 는 Node 22 여야 한다.** Node 20 에서 jsdom → undici 가
    `webidl.util.markAsUncloneable is not a function` 로 죽어 DOM 테스트가 로드조차 안 된다.
25. **`file://` 에서 localStorage 는 SecurityError 를 던진다.**
    try/catch 로 감싸지 않으면 앱이 통째로 죽는다 (`safeStorage()` 참고).
26. **React Flow 는 크기가 0 이면 엣지를 그리지 않는다.** jsdom 에서 배선 클릭을
    시험할 수 없었는데, 크기를 알려주는 관찰자를 물려 이제 시험할 수 있다.
27. **React Flow 의 엣지 레이어는 zIndex 속성으로 안 눌린다.** CSS 로 눌러야 한다
    (`.react-flow__edges { z-index: 0 !important; }`).

### 10-7. 판단

28. **각 경고에 왜 문제인지 한 문장을 붙여라.** "규칙 위반"만 적으면 고칠 수가 없다.
29. **자동으로 고치지 마라.** 끊어진 참조·중복 id·구간 길이 충돌은 알리기만 한다 —
    어느 쪽이 진짜인지는 사람만 안다.
30. **외부에서 참조할 수 있는 출력 형식은 함부로 바꾸지 마라.**
    접속표 CSV 기본 헤더는 발표된 인터페이스다.
31. **검증되지 않은 품번은 만들지 마라.** 시드 부품은 데이터시트 원문 값만 넣고,
    품번 규칙은 비고에만 적어 핀맵 에디터로 복제해 쓰게 한다. `gender` 도
    자료가 갈리면 비워 둔다(틀린 값보다 낫다).
